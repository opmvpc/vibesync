## 2. Frontières choisies

```c
/* platform.h */
typedef struct { Str8 name; b32 is_dir; b32 is_link; i64 size_bytes; } VsDirEntry;
typedef struct VsDirIter VsDirIter;             /* opaque, propre à l'impl. */
typedef struct {
    VsDirIter *(*open)(Arena *a, Str8 dir);     /* NULL si illisible */
    b32  (*next)(VsDirIter *it, VsDirEntry *out);
    void (*close)(VsDirIter *it);
    b32  (*name_eq_ci)(Arena *scratch, Str8 a, Str8 b);
    u8   sep;
} VsDirOps;
const VsDirOps *vs_dir_ops(void);
/* media.h */
b32 media_find_with(Arena*, const VsDirOps*, const StrBuf *dirs, isize, Str8, MediaFind*);
```

Points d'attention volontaires :
- l'itérateur rend `.` et `..` **bruts** : le compteur `visited` reste identique
  à celui de `FindFirstFileW` (des tests le vérifient) ;
- `name_eq_ci` reste PLATEFORME : sous Windows c'est toujours
  `CompareStringOrdinal` sur de l'UTF-16, longueurs comparées en unités UTF-16.
  Une comparaison ASCII côté portable aurait changé le comportement ;
- l'itérateur Win32 recycle sa place d'arène (marque posée après la structure,
  `arena_pop_to` à chaque entrée) : 50 000 entrées ne laissent rien derrière ;
  le parcours portable encadre chaque dossier d'une portée temporaire, donc la
  mémoire est bornée par la profondeur (≤ 6).
- Les autres primitives (arènes, `vs_now_ns`, `vs_random_bytes`, `vs_log`,
  `vs_fatal`, `vs_write_stderr`, UTF-16) gardent leurs prototypes dans `base.h`,
  seule l'implémentation change de fichier — zéro modification d'appelant.

## 5. Risques résiduels

- **Non compilé sous Windows ici** : `base_win32.c`, `vlc_win32.c`,
  `ini_win32.c`, `media_win32.c`, `test_win32.c` n'ont pu être que relus
  (équilibrage des blocs vérifié, jointures de découpe contrôlées ligne à
  ligne, inventaire des fonctions avant/après identique : 55 pour base, 31 pour
  vlc, 13 pour ini, 10 pour media).
- **`MEDIA_PATH_CAP`** passe de 32 768 unités UTF-16 à 32 768 **octets** : borne
  identique pour un chemin ASCII, plus conservatrice pour un chemin accentué
  très profond (> 32 Ko). Aucun cas réel connu ; c'est la seule différence de
  comportement possible de tout le lot.
- **UBSan pré-existant** (non introduit ici, code repris verbatim) :
  `base_core.c:250` (`str_to_i64`, ex-`base.c:461`) — `-(i64)acc` quand
  `acc == 2^63` sur l'entrée `"-9223372036854775808"`. Résultat correct en
  pratique (complément à deux), UB formel. À traiter dans un ticket dédié, un
  correctif ici aurait violé la règle « diff de logique nul ». Jamais vu
  jusqu'ici parce que `build.bat asan` n'active pas `-fsanitize=undefined`.
- **`test_core.c` lit les fichiers en `fopen/fread`** (harnais uniquement) et
  trouve `test/vectors` via `VsDirOps` : un chemin passé en argument reste
  prioritaire, donc la CI Windows garde son comportement actuel.
- Phase 2 (VS-031) n'a plus qu'à fournir `base_posix.c` + `media_posix.c` et
  compiler la liste `CORE_SHARED` telle quelle dans la cible SwiftPM `VSCore`.
