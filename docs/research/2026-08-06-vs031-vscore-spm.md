## 1. Emplacement : Package.swift à la racine du dépôt

SwiftPM refuse qu'une cible référence des sources hors de la racine du paquet ;
le lien symbolique était exclu (checkout Windows). La seule racine contenant à
la fois la couche C commune et le client macOS est celle du dépôt : **le
Package.swift a été déplacé de `ui/macos/` vers `/`**, et chaque cible pointe son
répertoire (`core`, `ui/macos/Sources/VibeSync`, `ui/macos/Tests/VibeSyncTests`).
Aucune source n'est dupliquée, aucun lien symbolique n'est créé, et `build.bat`
compile exactement les mêmes fichiers `core/src/*.c`.

Écartés : `core/` sous `ui/macos/` (le client Windows irait chercher son cœur
chez le client macOS), duplication/copie au build (deux vérités), symlink.

```
core/
  include/   base.h conn.h engine.h ini.h json.h media.h platform.h protocol.h
             vlc.h  +  module.modulemap        (contrat public, listé à la main)
  src/       base_core.c conn.c engine.c ini_core.c json.c media_core.c
             protocol.c vlc_core.c             ← compilé par build.bat ET VSCore
  posix/     base_posix.c media_posix.c        ← macOS seulement (VSCore)
  tests/     test_core.c test_util.h main_posix.c ubsan.supp
```

Restent chez le client Windows : `base_win32.c`, `media_win32.c`, `vlc_win32.c`,
`ini_win32.c`, `net.c`, `ui.c`, `health.c`, `secret.c`, `main.c`, `test_win32.c`,
`test_main.c` — pendants exacts de `core/posix`.

## 2. Cible VSCore

```swift
.target(name: "VSCore", path: "core", exclude: ["tests"],
        sources: ["src", "posix"], publicHeadersPath: "include",
        cSettings: [.headerSearchPath("include"),
                    .unsafeFlags(["-ffp-contract=off", "-Wall", "-Wextra", "-Werror",
                                  "-Wshadow", "-Wvla", "-Wstrict-prototypes",
                                  "-Wmissing-prototypes"])])
```

Mêmes drapeaux que `build.bat` (plus `cLanguageStandard: .c11` au niveau du
paquet) : ce qui échoue ici échoue là-bas. `module.modulemap` liste les neuf
en-têtes un par un plutôt qu'un umbrella — le contrat public se lit dans le
fichier. `test_util.h` n'appartient pas au module (il vit dans `core/tests`).
`VSCore` est consommé par la cible de tests **uniquement** ; l'exécutable
`VibeSync` ne le voit pas encore — c'est la phase 3 (VS-032).

## 3. Primitives POSIX : ce qui peut diverger de Windows

| Primitive | Windows | macOS/POSIX | Écart |
|---|---|---|---|
| arène | VirtualAlloc RESERVE/COMMIT | `mmap(PROT_NONE)` + `mprotect` par tranches de 64 Ko | aucun (bornes réalignées sur la page : 16 Ko en arm64) |
| horloge | GetSystemTimeAsFileTime | `clock_gettime(CLOCK_REALTIME)` | résolution ns au lieu de 100 ns |
| aléa | BCryptGenRandom | `arc4random_buf` (repli `getentropy`) | aucun |
| journal | `%APPDATA%\vibesync.log`, CRLF | `~/Library/Logs/vibesync.log`, LF | fin de ligne (le journal se lit avec `tail`) |
| UTF-16 | `utf8_to_utf16` / `utf16_to_utf8` | **non implémentées** | volontaire : rien côté macOS n'en a besoin, la couche commune ne parle qu'UTF-8 (risque n°1 d'ADR-010). Lien impossible si un jour quelqu'un les appelle — c'est le but. |

**`name_eq_ci` — le point à surveiller.** VS-030 avait gardé cette comparaison
côté plateforme exprès : sous Windows c'est `CompareStringOrdinal` sur de
l'UTF-16, donc un repli de casse Unicode COMPLET. Sans table (ADR-008 interdit
d'en importer une), l'implémentation POSIX couvre **l'ASCII et le supplément
Latin-1** (`À-Þ` ↔ `à-þ`, hors `×`), comparés point de code par point de code —
pas octet par octet, et jamais en octets pour la longueur. Divergences possibles,
toutes en direction « macOS trouve moins que Windows » :

1. **Hors Latin-1** : `Ω`/`ω`, `Я`/`я`, `İ` turc, `Ÿ`(U+0178)/`ÿ` ne se replient
   pas. Windows les tiendrait pour égaux.
2. **Normalisation** : HFS+ rend les noms en NFD, APFS préserve ce qu'on lui a
   donné, NTFS stocke tel quel (en pratique NFC). `é` (U+00E9) et `e`+`◌́`
   (U+0065 U+0301) ne sont donc PAS égaux ici, alors que le volume lui-même les
   considère comme le même fichier. C'est l'écart le plus probable en vrai : un
   nom tapé sous Windows et un nom lu depuis un volume HFS+ peuvent ne pas se
   reconnaître.
3. `ß` n'a pas de majuscule simple ; identique des deux côtés, pour une fois.

Conséquence pratique : `media_find` peut rendre « non trouvé » sur macOS là où
Windows trouverait. Jamais un FAUX positif — c'est le sens qui coûte le moins
cher (l'utilisateur choisit son fichier à la main). À traiter par un ticket
dédié si le cas se présente en séance réelle, pas ici.

Autres choix de `media_posix.c` : entrées rendues BRUTES (`.` et `..` compris,
pour que le compteur `visited` reste celui de `FindFirstFileW`) ; `d_type` sert
pour les dossiers et les liens, `lstat` n'est payé que pour les fichiers
ordinaires et les entrées de type inconnu (il faut leur taille) ; `S_ISLNK` d'un
`lstat` joue le rôle de `FILE_ATTRIBUTE_REPARSE_POINT`, donc les liens ne sont
jamais suivis ; l'itérateur recycle sa place d'arène à chaque entrée, comme la
version Win32. `media_default_dir` : `~/Downloads`, repli `~/Movies` puis `~`.

## 4. Rejeu des vecteurs via l'API C

`ui/macos/Tests/VibeSyncTests/VSCoreVectorsTests.swift` (417 l.) reproduit
`run_vector` de `test_core.c` au geste près — mêmes appels, même ordre, même
règle `keepOutput`. Le décor reste Swift (lecture du vecteur, `FakeVLC` partagé
avec `VectorsTests`) ; tout ce qui est JUGÉ passe par le C : `vlc_parse_status`
(donc `json.c` + `vlc_core.c`), puis `engine_on_welcome` / `_pong` /
`_roomstate` / `_vlc_status` / `_tick`, et les libellés comparés viennent de
`vs_cmd_name` / `vs_msg_name` / `vs_action_name` / `vs_play_state_name`.
Trois ponts d'interop seulement : `Str8` le temps d'un appel, `StrBuf` relu en
`String`, et les tableaux fixes de `VsOutput` (importés en tuples) relus comme
des tampons. `VectorsTests.swift` (moteur Swift natif) n'a pas bougé et reste
vert : double couverture, aucun retrait.

Contre-épreuve : en perturbant volontairement la comparaison du drift, le test
remonte 147 échecs — il compare bien. Un plancher sur le nombre de pas rejoués
(146 aujourd'hui) protège du rejeu qui ne compare rien.

## 6. Ce que la CI Windows doit confirmer

1. **`build.bat test`** avec les nouveaux chemins : `CORE_DIR=%ROOT%..\..\core`,
   `INC=-I core\include -I ui\win32\src`, `TESTINC=-I core\tests`,
   `TESTS=test_main.c + core\tests\test_core.c + test_win32.c`. Aucune source
   n'a changé de contenu, seulement de répertoire : **le total de vérifications
   doit être exactement celui d'avant** (les 8 vérifications du parcours simulé
   restent sous `#ifndef _WIN32`).
2. **`build.bat`** (release) : l'exe reste sous 500 Ko, `%INC%` ajouté à la ligne
   de compilation.
3. **`build.bat asan`** : inchangé fonctionnellement.
4. Le quoting cmd de `INC`/`TESTINC` suit celui, déjà éprouvé, de `CORE_SHARED`
   (`set "X=-I "a" -I "b""`) ; aucun chemin ne se termine par une contre-oblique,
   donc rien n'échappe le guillemet fermant. C'est le seul point du lot qui n'a
   pas pu être exécuté ici.

  dans Package.swift.

  encore injecté côté SwiftPM (`VS_VERSION` y vaut « dev ») — à faire quand le C
  entrera en production sur macOS.
